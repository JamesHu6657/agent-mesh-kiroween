### 5a. M3 gate fixes (m3-gatefix, Linear gate review P1-1, P1-2)

Linear's gate review of main `8602d33` (REVISE) reproduced two cleanup gaps that L1 does not cover (the member never leaves the run's process group):

- **P1-1 recovery adopt.** `recovery._adopt()` returned without recording the group members; `track_adopted_seen()` ran only on a later watch tick with the wrapper still alive. A wrapper exiting between adopt and the first watch left a same-group env={} child alive while the run closed and `task:<id>` was released. Fix: `_adopt()` calls `supervisor.establish_adopted_seen()` before it returns (the same scan, counted only if the wrapper pid + starttime still hold after it; members in memory and `seen.json`); the first watch tick rescans; if the wrapper is gone by then, the watch uses the adopt-time members for the two-scan termination. The past-deadline adopt path passes them to `begin()`. **Round 2 (Linear re-review P1):** if the wrapper identity is gone after the adoption scan (it exited anywhere between the identity check in `_recover_run` and the end of the adoption scan), the scan is discarded and is never read as "no members": `establish_adopted_seen()` returns False, the seen state is marked unusable (reason `adopt_scan_untrusted`), recovery persists the hold (`seen_hold:<run_id>`) and `run.seen_unusable` at once and returns `adopted_uncertain` (`daemon.recovered` `runs_adopted_uncertain`). The r4b hold keeps the run open and `task:<id>` held while any process is in the run's pgid/session; nothing is signalled by pgid alone (MESH_RUN_ID carriers still are); an operator resolves it with `run release --force-seen-unusable`, or the run closes once the group is empty. Tests: `test_wrapper_exits_during_adoption_scan_fails_closed` (real scan, then a scheduling hook makes the wrapper exit before the identity re-check) and `test_wrapper_exits_after_identity_check_before_adoption_scan` (wrapper exits just before the scan); `test_adopt_past_deadline_hands_adoption_members_to_termination` pins the deadline-path handoff. **Rounds 3–11 (Linear, Quest, Carbon reviews):** an old valid seen.json, a failed invalidation, a failed adopt transaction or a crash before the hold row could let the run close `lost` with the member alive. Now `recovery._adopt` first marks the run unusable in memory (with a hold token) and then replaces seen.json with a durable `adopt_pending` marker (tmp + fsync + rename + dir fsync; no `members`, but `prior_members`: every identity recorded so far, so setsid escapees outside the pgid/session stay termination targets), all before the adopt transaction; a trusted adoption scan replaces it with members, an untrusted one rewrites it as `adopt_scan_untrusted` and keeps the members known before the scan. Adoption holds carry a token (memory and hold row); a seen.json without it is unusable. Whenever a hold row is due, `run.seen_unusable` commits in the same transaction as it (adoption and watch flush); once a hold row is already persisted, an event-only write is possible. Round 6 adds one close-safety gate in `_close_run`, the only meshd function that closes a task run and releases its lease. It takes the identity from the DB or `wrapper.json` (spawn window) and the recorded members from memory and disk (incl. `prior_members`). It refuses the close while a recorded identity lives (it is terminated first) or while the run's pgid/session is occupied and still the run's (held). Only `run release --force-seen-unusable` bypasses it. The audit of every close/lease-release site is in `docs/impl-notes-m3-gatefix.md` (lead turns are not routed through it: L4). Round 7: recovered merge_test runs pass an equivalent gate (`merge_close_gate`; occupied group → run open, `merge:<prj>` kept, `merge.recovery_blocked`, re-checked only at boot: known limitation, `run release` does not cover it, so `merge:<prj>` stays blocked until meshd restarts even after the occupant exits; a `kill_failed` termination keeps its recorded deviation). A gate-initiated cleanup of a run that ended on its own keeps its outcome (leftovers, H17: exit 0 → auto-submit). An unknown wrapper starttime fails closed (held, nothing signalled); round 8: it is never promoted to a trusted identity (`wrapper_alive` false, no seen scan, no termination target, stored as NULL). A spawn that fails after Popen (registration or identity read) kills the wrapper's group through the unreaped Popen handle before the run closes `spawn_failed`; round 8: `MESH_RUN_ID` carriers outside the group (setsid escapees) are killed and recorded too, and if anything survives the run stays open with its lease and the wrapper unreaped while the watch pass retries (closed `spawn_failed` only once everything is gone); round 9: authenticated (pid, starttime) carriers are kept, retried by identity (not by env rescan) and persisted as seen.json `prior_members` for boot recovery and the close gate; an error inside the abort keeps it pending; the orphan reaper never reaps a pending abort's wrapper.
